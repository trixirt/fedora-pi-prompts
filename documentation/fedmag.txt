# Using Fedora AI to Help Fedora

*How a Fedora package maintainer uses pi-coding-agent and fully local AI for real packaging work*

## Introduction

Last release cycle I was maintaining the ROCm stack for Fedora with 40+ packages, each generating pages of review and test output. Reading through another 800-line test log felt like the fastest path to done, and I was wrong every time. Local AI changed that: [pi-coding-agent](https://github.com/earendil-works/pi/tree/main/packages/coding-agent), running against Qwen models that never leave my machine, now parses test logs, flags spec file problems, and compares failing builds against known-good baselines in seconds. This article shows how to set it up on Fedora and what I actually use it for when I work on Fedora packages.

Pi-coding-agent has become indispensable for Fedora package maintenance. It doesn't replace human expertise but augments it — taking the drudgery out of the work so you can focus on the parts that require human judgment and creativity.

The fedora-pi-prompts repository provides pre-built prompts for Fedora-specific tasks, so you don't need to start from scratch. It includes prompts for build regression, package review compliance, and test failure analysis — all tailored to Fedora packaging workflows.

## What is pi-coding-agent?

pi-coding-agent (or just "pi") is an open source coding agent that lives in your terminal. It reads files, runs commands, and explains failures — but you control what it touches, and every step is visible.

What makes it interesting for Fedora is that it can be pointed at a local LLM server such as [Ollama](https://ollama.com/). Your code, specs, and build logs never leave your hardware, and it works fine on a laptop without a datacenter GPU. Both pi and Ollama are Fedora packages, so the entire stack installs with dnf — no COPR, no manual downloads. This makes it easy to get started with local AI on Fedora.

Pi is built around a few principles that matter for packaging work. It is privacy-first by design: inference happens on your machine, and nothing is sent to a cloud API unless you explicitly configure it to. It is extensible — behavior can be shaped with extensions, skills, and prompt templates, making it adaptable to different workflows — and it is backend-agnostic, talking to Ollama, llama.cpp, vLLM, or other local LLM servers. For this article, Ollama plus Qwen is all you need.

## Getting started

Everything below works on Fedora Workstation and Server. I even used this setup on Atomic edition, which works just as well as the full desktop variant. Budget about 8GB of RAM for small models, 16GB+ for comfortable use, and any recent AMD or Intel CPU. A GPU helps a lot. On AMD systems, ROCm is what makes the big models practical and fast enough for interactive use.

### Install

```bash
sudo dnf install ollama pi-coding-agent
sudo systemctl enable --now ollama
```

pi wires itself to Ollama through the launch integration:

```bash
ollama launch pi
```

That configures Ollama as pi's model provider and drops you into an interactive session. Use `ollama launch pi --config` to configure without starting a session. The launch integration simplifies setup so you can get to work rather than configuration.

Verify the pieces are talking to each other:

```bash
ollama --version
pi --version
```

Once everything verifies, start pi in any directory and ask it something harmless, like summarizing the spec file sitting in front of you. If it reads the file and answers, your local stack is working end to end

### Pick a model that fits your RAM

My daily driver is a [Framework Desktop](https://frame.work/desktop) with an AMD [Strix Halo](https://www.amd.com/en/products/processors/consumer/ryzen-ai/ai-pc-experiences.html) processor (Radeon 8050S, gfx1151). With ROCm installed, larger models run several times faster. For packaging work, I rely on this acceleration for model loading and prompt processing. On CPU-only systems, smaller models will still work but may take longer to respond. If you're running out of RAM, Ollama's `OLLAMA_KV_CACHE_TYPE=i8` setting can help reduce memory usage.

## Real-World Use Cases for Fedora Users

### 1. Diagnosing Build Failures with mock-build-regression

**Problem:** When a package build fails during mass rebuilds with hundreds of packages, tracking down the root cause can take hours of manual log analysis. Each failure produces verbose output that needs careful interpretation to determine if it's a real issue or a transient build problem. The sheer volume of logs makes it difficult to see patterns across failures.

**Example workflow:**

```bash
# Copy the build log from a failed mock build
cp /var/lib/mock/fedora-rawhide-rawhide/result/failed-package.log .

# Run the regression analysis prompt
pi < ~/ai/fedora-pi-prompts/mock/mock-build-regression.xml
```

The prompt analyzes the log against known-good build patterns I've tracked over previous releases. It identifies:
- Whether the failure is a new issue or a known transient problem
- Which dependencies might be affected
- What changes in the package or its dependencies could be causing the failure

**How AI helps:** Instead of spending hours parsing through hundreds of lines of build output, I get a concise summary that highlights the likely causes. This lets me focus on fixing real issues rather than diagnosing known problems. The AI remembers the baseline of previous successful builds and flags deviations.

### 2. Automated Package Review with fedora-review Prompts

**Problem:** Each Fedora package must pass the `fedora-review` tool, which generates pages of output covering dozens of packaging requirements. Manually reviewing each item against the Fedora Packaging Guidelines takes time and is error-prone, especially when you have 40+ packages to review.

**Example workflow:**

```bash
# For each package in the stack
for pkg in /sfs/rocm/*/; do
  cd "$pkg"
  pi < ~/ai/fedora-pi-prompts/fedora-review/fedora-rpm-english.xml
  pi < ~/ai/fedora-pi-prompts/fedora-review/fedora-rpm-patch.xml
  pi < ~/ai/fedora-pi-prompts/fedora-review/fedora-rpm-fonts.xml
  pi < ~/ai/fedora-pi-prompts/fedora-review/fedora-rpm-globals.xml
  pi < ~/ai/fedora-pi-prompts/fedora-review/fedora-rpm-macros.xml
  pi < ~/ai/fedora-pi-prompts/fedora-review/fedora-rpm-extra-bins.xml
  pi < ~/ai/fedora-pi-prompts/fedora-review/fedora-rpm-preserve-time.xml
  pi < ~/ai/fedora-pi-prompts/fedora-review/fedora-rpm-changelog.xml
done
```

The benefit: Instead of manually reading through pages of review output for each package, you get concise summaries addressing each Fedora requirement. For the major ROCm 8.x update (F45), batch runs like this cut the review analysis from days to hours across 40+ packages — I could focus on the actual fixes while pi worked through the logs.

**How AI helps:** The batch processing runs all 8 prompts for all 40+ packages in a single command. Instead of manually reviewing each package against each of the 8 requirements, I get concise summaries highlighting only the items that need action. This reduces review time from days to hours, and I can continue working on other packages while the AI analyzes each one.

### 3. Analyzing Test Failures with Test Prompts

**Problem:** ROCm includes dozens of packages that each run hundreds or thousands of tests. When tests fail, the output spans hundreds of lines, and determining whether a failure is a real bug, a test environment issue, or a known flake requires careful analysis across many test logs.

**Example workflow:**

```bash
# Copy test output from containerized builds
cp /sfs/rocm-distro-containers/fedora/rawhide/hipblas/check/output/test.log .

# Run analysis prompts
pi < ~/ai/fedora-pi-prompts/test/docker-pkgdiff.xml
```

The prompts analyze the test output to produce:
- Summary of pass/fail/skip counts
- GPU architecture verification
- Version compatibility check
- Identification of which tests failed and whether the failures are expected

**How AI helps:** Instead of manually reading through test logs for each package, I get structured summaries that make it easy to see at a glance which issues are real bugs versus expected behavior. For the ROCm 7.2 compatibility stack targeting F46, this reduced test analysis from hours to minutes per package — I could focus on actual fixes while the AI identified which failures needed attention.

## fedora-pi-prompts: Fedora-Specific Prompts

The [`fedora-pi-prompts`](https://github.com/trixirt/fedora-pi-prompts) repository contains ready-to-use prompts for Fedora workflows:

- `fedora-review/` - 8 spec file compliance prompts
- `mock/` - mock build regression analysis
- `test/` - Docker container test analysis

Each prompt is an XML file that contains system instructions, example outputs, and the content to analyze. For example, the `fedora-rpm-english.xml` prompt asks the model to fix British-to-American spelling issues in RPM spec files.

## Things to Watch Out For

A few honest caveats: the prompts are helpers, not gatekeepers. Every spec change pi makes should pass `fedora-review` and your review before shipping. Smaller models make smaller mistakes — a 4B model will confidently "fix" the wrong file if the prompt is ambiguous, so read the diffs.
