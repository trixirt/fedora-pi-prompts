# Using Fedora AI to Help Open Source

*How Fedora users leverage pi-coding-agent and local AI to contribute to open source projects*

## Introduction

The pi-coding-agent is now part of Fedora 45. This article introduces the tool for an end-to-end open source agentic AI stack. Over the course of the Fedora 45 development period I have been using pi to do real day to day work for Fedora and want to share this tool with the rest of the community.

## What is pi-coding-agent?

[pi-coding-agent](https://pi.dev/) (or just "pi") is an open source coding agent. It runs on your machine, reads files, runs commands, and explains failures — but you control what it touches, and every step is visible.

What makes it perfect for Fedora is that it can be pointed at local LLM servers already in Fedora, such as [Ollama](https://ollama.com/) and [llama.cpp](https://llama-cpp.com/), with [gufo](https://github.com/gufo-org/gufo) and [colibri](https://github.com/JustVugg/colibri) coming in Fedora 46.

Pick the Fedora LLM server you want.

We are using Ollama in this article because it is the easiest to integrate with pi.


## Getting started

### Install

```bash
sudo dnf install ollama pi-coding-agent
sudo systemctl enable --now ollama
```

### Pick a model that fits your GPU's VRAM

| VRAM | Recommended Model | Notes |
|-----|-------------------|-------|
| **64GB** | [`qwen3-coder-next:latest`](https://ollama.com/library/qwen3-coder-next) | 80B MoE (3B active per token, ~52GB download), excellent quality |
| **32GB** | [`qwen3.8:27b`](https://ollama.com/library/qwen3.8) | 27B (~18GB download), very good quality |
| **16GB** | [`qwen3:8b`](https://ollama.com/library/qwen3) | 8B (~5.2GB download), good coding, leaves room for other work |
| **8GB** | [`qwen3:1.7b`](https://ollama.com/library/qwen3) or [`qwen3:4b`](https://ollama.com/library/qwen3) | 1.7B (~1.4GB) or 4B (~2.5GB) download, quick, responsive, adequate for simple tasks |

Note: Use the biggest model your hardware can handle and experiment from there — the quality difference is worth it. The model used in the use cases is qwen3.8:27b.

For more information on Qwen models, see the [Qwen3 documentation](https://www.alibabacloud.com/help/en/model-studio/qwen3-8-27b).

Install a model:

```bash
ollama pull qwen3.8:27b
```

pi wires itself to ollama through the launch integration:

```bash
ollama launch pi --config
```

That configures ollama as pi's model provider and drops you into an interactive session. ollama will take you some choices, mostly to pick the model you just downloaded. After this one config set, you can use pi directly.

```bash
pi
```

Once this is working, try pi on any open source project you're working on. Start pi in any directory and ask it to analyze the project and provide a summary. Then use pi's help to explore whatever interests you — whether it's understanding the codebase, suggesting improvements, or debugging issues. This is your local AI assistant, ready to help you learn and work with any codebase.

## Real-World Use Cases from a Fedora Packager

In the Fedora project, I am a packager, responsible for maintaining AI packages and the ROCm stack. Here are some real world uses of using the same AI that I am maintaining to help with my day to day work. The prompts come from a personal project [fedora-pi-prompts](https://github.com/trixirt/fedora-pi-prompts)

### 1. Diagnosing Build Failures with mock-build-regression

**Problem:** When a package build fails during mass rebuilds with hundreds of packages, tracking down the root cause can take hours. The sheer volume of logs makes it difficult to see patterns across failures.

**Example workflow:**

```bash
cd <package>
# Update the package and do a build
mock <package>.srpm
# Waiting for mock to finish
# Some failure happens during build
cp <path-to-successful>/results/build.log .
pi < ~/fedora-pi-prompts/mock/mock-build-regression.xml
```

The prompt analyzes the log against known-good build patterns I've tracked over previous releases. It identifies:
- Finds the problem area in the build
- Does an initial triage of the problem
- Proposes a fix

**How open source AI helps:** Instead of spending hours parsing through build output, I get a concise summary that highlights the likely causes.

### 2. Automated Package Improvement with fedora-review Prompts

**Problem:** Fedora packages need to stay compliant with the Packaging Guidelines as they evolve. Refreshing existing packages to match updated guidelines can be tedious, especially when maintaining dozens of packages. Manually reviewing each package for compliance takes time and is error-prone.

**Example workflow:**

```bash
for pkg in ~/<path-to-packages>/*/; do
  cd "$pkg" || continue
  pi < ~/fedora-pi-prompts/fedora-review/fedora-rpm-english.xml
done
```

**How open source AI helps:** Instead of manually reviewing each package for compliance, you get automatic suggestions for improvement.

### 3. Analyzing Test Failures with Test Prompts

**Problem:** Fedora ROCm packages have test subpackages that each run hundreds or thousands of tests. When tests fail, the output spans hundreds of lines, and determining whether a failure is a real bug, a test environment issue, or a known flake requires careful analysis across many test logs.

**Test container:** The [rocm-distro-containers](https://github.com/trixirt/rocm-distro-containers/tree/main/fedora/rawhide/hipblas) repository contains container-based testing targeting Fedora and other Linux distributions like Ubuntu, Debian, and Arch. Each package has subdirectories with tests organized according to the [ROCm Testing](https://fedoraproject.org/wiki/SIGs/HC#Testing) table.

**Example workflow:**

```bash
cd <path-to-tests>/hipblas/copr-preview-pkgdiff
./run.sh
```

The [run.sh](https://github.com/trixirt/rocm-distro-containers/blob/main/fedora/rawhide/hipblas/copr-preview-pkgdiff/run.sh) script builds the docker, then runs the docker collecting test output, and finally runs pi to analyze it, producing:
- Summary of ABI changes and an evaluation of seriousness
- Summary of package manifest changes

**How open source AI helps:** Instead of manually reading through test logs for each package, I get structured summaries that make it easy to see at a glance which issues are real bugs versus expected behavior.

## Things to Watch Out For

A few honest caveats: AI prompts are helpers, not gatekeepers. AI will confidently "fix" something that may not be broken.

## Conclusion

Open source AI is not about replacing maintainers; it is a tool to help you do the tedious parts of open source work on your own hardware, on your own terms, while keeping your code and data under community control.
